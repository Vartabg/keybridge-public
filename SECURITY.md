# Security boundary

Keybridge 0.1 is a developer prototype that reduces accidental credential
disclosure. It is **not a hardened vault boundary against an unrestricted local
agent, malware, administrator, or another process running as the same user**.
File permissions do not isolate programs sharing an OS identity. Such a program
can change this source/configuration, inspect process state where the OS allows,
impersonate a local client, or consume an approved allowance. A claimed project
name would not fix that; this version does not claim per-project authorization.

## What is implemented

- Owner startup unlocks Bitwarden in a private terminal. The master password and
  vault session are never returned through the agent protocol, saved by Keybridge,
  or put in command arguments. Bitwarden subprocess output is captured.
- Password and session values exist transiently in the Bitwarden subprocess
  environment; this is observable to sufficiently privileged/local software.
- A dedicated Bitwarden CLI profile prevents Keybridge from locking unrelated
  CLI sessions. Bitwarden itself manages its encrypted local cache and login
  state. Keybridge does not replace that storage or authentication implementation.
- Keybridge locks that profile before opening its agent socket, retaining only
  the selected provider credential in broker state. Startup drops inherited
  environment entries other than a small OS/terminal allowlist. Provider calls
  do not fall back to existing environment keys.
- References/settings use permission 600 and the app folder permission 700.
  A Unix socket is used instead of a public/browser HTTP server.
- The provider URLs and authentication headers are generated by fixed adapters.
  No arbitrary URLs, tools, headers, redirect following, proxy-environment
  inheritance, or child-process execution is exposed to agent requests.
- Attempts are reserved atomically. Failed/unknown network outcomes count and
  are not automatically retried. Session lock/expiry denies future calls.
- Outputs are parsed to supported text. Raw provider error bodies and exception
  details are discarded. Known exact key/URL-encoded/base64 values are redacted.
- Audit events contain provider, model, time, attempt and outcome, not prompts,
  responses, key prefixes or key hashes. Events are in memory only.

## Limits that matter

The configured service receives the prompt; it is not made private by using this
broker. The approved account can still incur charges. Attempts and output-token
limits are not dollar caps and are not guaranteed to bound provider-specific
reasoning charges. Apply spending controls at the provider.

All same-user clients share one session policy. Revocation cannot recall a
request already transmitted or undo its costs. The key stays in an in-flight
worker until it returns even if the broker is locked. Python strings are not
securely zeroized; clearing references is not a claim of forensic memory erasure.
Swap, crash dumps, imported libraries, and OS-level attacks are outside this
prototype's boundary. Redaction is defense in depth, not proof against arbitrary
encodings or exfiltration through compromised upstream software.

TTY checks do not establish that a human is present. Only enter credentials in
your own trusted terminal, never a terminal being captured by an AI agent.
The TypeSafe owner flow can run initial `bw login --quiet` in that private
terminal; quiet mode suppresses the login session value. Login and 2FA are
handled by Bitwarden. Never copy its output into chat.

## Owner-only TypeSafe/Vercel provisioning

This separate CLI workflow reads the owner's chosen vault field, locks the
dedicated Bitwarden profile, makes one fixed non-personal TypeSafe/Jev check,
then stores `TYPESAFE_API_KEY` as a sensitive Vercel variable for the explicit
project, team and environments. That check may incur the normal API charge.
Only the fixed TypeSafe endpoint receives the check; no redirects or inherited
proxies are used. Vercel's official authenticated CLI receives the key on stdin,
never in arguments, environment variables or an intermediate plaintext file.
CLI/API output is captured and reduced to validated metadata or safe errors.

The local connection receipt contains vault references, destination IDs, an
operation marker, provider-check time and variable ID, not the key or its hash.
It is written atomically with mode 600. A local advisory lock prevents two owner
setups from racing. An uncertain write is checked using its exact remote
metadata marker; it is not blindly repeated. Existing variables are never
overwritten. The workflow does not deploy a site or expose provisioning via
the agent socket.

Vercel retains the key for future deployments. Broker session limits and local
`keybridge lock` do **not** restrict or revoke cloud usage. Revocation requires
removing the Vercel variable and replacing affected deployments, or revoking
the credential at TypeSafe. Vercel project access and provider spending controls
remain independent of Keybridge. Changing the local project link changes the
proposed destination, which is displayed to the owner and verified remotely.

Before release beyond a local prototype: independent security review, reviewed
OS isolation/signed owner application, real Bitwarden login/2FA/timeout tests,
provider acceptance tests under a user-approved budget, and accessibility and
usability checks for the eventual desktop interface.

The separate TypeSafe owner workflow has September 25, 2026 acceptance evidence:
private owner setup, sensitive-variable metadata, and one live Preview query on
the owner's own project.
This is personal usage evidence, not outside-customer demand. The local broker
with live providers, repeat owner onboarding and production use remain
unverified. Same-OS-user hostile-process isolation is unsupported.

The guided fake-key demo uses a fresh private temporary folder, the real local
transport and policy, and a fixed in-process fake response. It does not open the
vault, invoke a provider or change Vercel. Its output is demonstration evidence,
not a new live acceptance result.

## Rust daemon

The Rust version of the session daemon in `rust/` has this same boundary. It is
not a stronger isolation claim. Same-OS-user hostile-process isolation is still
unsupported.

What differs: the daemon's own copy of the key is overwritten with zeros when
the session locks, expires, uses up its attempts or stops. Copies made by the
HTTP and TLS libraries, the terminal, kernel buffers, swap and crash dumps are
not covered, and an in-flight request keeps the key until it returns. The crate
has no `unsafe` code of its own; its dependencies have not been audited.

Unlike the Python version, the Rust daemon does not clear inherited environment
variables at startup. It never reads a key from the environment, starts no
child process, and its HTTP client ignores proxy variables.

Its `start` command reads one key at a hidden prompt and requires a real
terminal. As with the Python flow, a terminal check does not prove a human is
present: enter a key only in your own terminal, never one an AI agent captures.
The Bitwarden unlock is not ported, so this path moves the key by hand once
per session. Nothing is written to disk.

Checks so far use made-up values, a local test server and the fake-key demo.
No live provider call has been made from the Rust client. See
[docs/rust-port.md](docs/rust-port.md).
